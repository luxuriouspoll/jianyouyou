# 简优优 · 简历优化原则（详细版）

> 本文件为公开的简历优化方法论细则，供 AI 优化 Agent 遵循：只基于用户已确认真实内容做改写与重组，严禁编造任何事实。

> **列表规范（全局）**：列表类型不做强制——工作经历主要职责可用有序（1. 2. 3.）或无序（-），选一种并保持同一类列表一致即可；其余版块（专业技能、项目明细、荣誉/证书、个人优势等）建议统一用无序列表（-）。关键是**一致、清晰**，不要混用导致混乱。

## 〇. 诊断前提（先明确背景，再下结论）
1. 先明确目标岗位（方向 / 招聘 JD）与候选人情况（应届生、工作年限、求职方向 / 状态）。
2. 判断每个项目 / 经历是否与目标岗位匹配：不匹配或只是工具性小项目，要么归并到工作经历 / 技能，要么深化描述。
3. 判断内容深度：是否只是“做了什么”而缺“为什么 / 结果”，是否过于简单；过简的要提示补充真实细节（不编造）。
4. 评价“项目是否合适 / 是否太简单”必须结合岗位要求，不能脱离岗位泛泛评价。
5. **完整性检查**：检查常见版块是否齐全（基本信息、教育背景、专业技能、实习/工作经历、项目经历、证书/荣誉、个人优势）。缺版块（如无证书/荣誉、无实习经历）要在“内容完整度”维度指出，并给**可补充建议**（无实习→建议补充校园经历/竞赛/项目；无证书→建议补充奖项/证书并注明来源），**严禁编造**。

## A. 真实性（最高优先，不可违背）
1. 只基于用户已确认的真实经历改写与重组。
2. 禁止新增或篡改：姓名、联系方式、公司、项目、职责、技能、证书、日期、量化数字、成果。
3. 缺失信息：提示补充，或标记为“待完善”，绝不自行推断为事实。
4. “包装”仅限用户已真实做过且能解释的内容；严禁凭空捏造。
5. **允许修正明显的拼写 / OCR / 术语错误**（可从上下文确认），如 BsckOff→BackOff、Kuborad→KubeBoard、DCND→CDN、Outofcpu→OutOfCPU；只改写法与大小写，不改变事实语义。

## B. 排版
1. 版面尽量写满一页；内容少时通过字号、行距、间距合理填充，不显空洞。
2. 全篇字体、字号、颜色、间隔统一；不要混用多种风格。
3. 教育背景不单独成行，合并到姓名下方（学校 / 专业 / 年份）。
4. 去掉“所学课程”这类冗长罗列。
5. 证书 / 荣誉单独区域，命名为「荣誉 / 证书」；各项用**无序/有序列表（-）**列出。
6. 重点内容加粗，方便招聘者快速定位。
7. **求职意向并入基本信息**（姓名 / 联系方式 / 教育 / 求职意向 一句话），不要单独建「求职意向」版块。

## C. 专业技能
1. 按**目标岗位**确定核心技能栈，不要固定成某一类岗位。例如：运维岗可包含 Linux、Nginx、Kubernetes/Docker、MySQL、监控（Zabbix/Prometheus）、Shell/Python；开发岗写所用语言/框架/工具；测试、数据、产品等岗位同理写其核心技能。
2. **按类别连排分组**：同类技能连续写在一起（不分段、**不加“分类：”标签前缀**），一条一条用**无序列表（-）**。示例：运维岗可先连续写容器/编排，再系统/网络，再数据库/监控；开发岗可先语言/框架，再中间件、工程化；测试岗可按用例类型、自动化层次分组。与目标岗位最相关类别放最前。避免长句堆砌、删除重复项。
3. 过细技能合并为一项（如“熟悉 Docker、K8s”合并为“容器：Docker / K8s”），合并后不再限制技能条数；但需按类别分组、去重，避免长句堆砌。
4. 围绕目标岗位相关收敛；有开发背景可补充开发技能。
5. **突出匹配点**：与目标岗位最核心的技术用**加粗**标出或放该类最前（示例：运维/云原生→K8s / 容器、SRE→监控 / 稳定性；开发→语言 / 框架 / 中间件；测试→自动化框架 / 接口 / 性能；数据→数仓 / ETL / 指标体系 —— 按目标岗位替换）；整条技能**不要出现“分类：”前缀**。

## D. 个人优势 / 自我评价
1. 每条优势用**无序列表（-）**列出，且必须能说出证据或事实（数字、产出、案例、具体场景）。
2. 反例：只写“沟通能力强、认真负责、自学能力强、学习能力强、动手能力扎实、抗压能力强”而无证据 = 空话，应删除或改写为有证据的表述，绝不允许原样保留。
3. 改写方式：把抽象能力落到“在什么项目/场景下、做了什么、取得什么结果”。例如“自学能力强”改为“独立自学并落地了 XX（如 Kubernetes/自动化脚本），在 XX 项目独立完成 XX”；“动手能力扎实”改为“独立完成 XX 的搭建/部署，解决 XX 问题”。若简历中无对应事实，标记为 missing，并引导用户在“补充信息”环节提供，严禁编造。
4. 技术内容放技能/项目；优势写软技能（总结沉淀、文档习惯、协作、责任心、学习能力、问题排查），软技能同样必须有事实/产出支撑。
5. “自我评价”与“个人优势”是同类内容，只保留一个区域（合并去重），不得保留两份重复的空话。

## E. 工作经历
1. 每条直接写工作内容，避免空泛职责描述。
2. 有帮助/成果的，在该条后续加一行，用数量与结果说明（提升、缩短、覆盖、节省、故障率等）。
3. 经历不要过于简短，易显得“混日子”；用户真实做过且懂的细节都可补上。
4. **按 STAR 组织**：一句背景/任务（S/T）→ 具体行动（A）→ 结果（R，量化）。S/T 一句带过，A 和 R 是主体。
5. 主要职责用**有序（1. 2. 3.）或无序列（-）**列出，选其一并保持一致即可；有成果的在该条后另起一行用一句话或无序列表说明。
6. **成果单独成行/成段**，不与职责混写；每条成果用量化或结果表述。
7. **成果归属**：事项/单点结果写在对应的职责或事项里（内联即可），不必单独列为“成果”；“成果”栏只写本段经历的**总体结果/亮点**（如 成本整体下降、覆盖规模、稳定性、关键贡献），不要逐条重复职责里已有的单点结果。
8. 结构示例：公司 / 团队 / 职位 / 时间（S/T）；主要职责：1…2…3…（A）；成果（R，量化、总体化）。

## F. 项目经历
1. 每个项目：名称 + 时间 + **角色**（负责人 / 核心开发 / 参与 / 独立完成）；若原文未写明角色，按事实补为“参与”或“独立完成”，不虚构。
2. **按 STAR 组织**：背景/角色+目标（S/T）→ 具体动作（A）→ 量化成果（R）。开头一句话点明背景与所用技术（S + 技术栈，不单出技术栈行）。
3. 技术栈与项目描述合并去重：技术栈信息只出现一次——在项目描述开头用一句话点明该项目用到的核心技术即可；不要在项目描述/主要工作里再重复罗列同一批技术名词，也**不要再单独输出一行“技术栈：…”**（项目描述已覆盖时）。
4. 主要工作 / 明细用**无序列表（-）**列出；具体动作（A）在同一层级用无序，不必转有序。
5. 每个项目必须有“项目成果”（R，数据化）。示例（按目标岗位替换）：运维岗——覆盖 200+ 台服务器、故障发现时间缩短 60%、可用性 99.95%；开发岗——请求量 / QPS、接口耗时、报错率；测试岗——用例覆盖率、线上漏测率、回归效率提升；数据岗——任务调度及时率、数据质量 / 口径统一。
6. 最有含金量的项目放最前；内容庞杂的拆分为独立项目（示例：运维可拆 DevOps / 监控 / ELK；开发可拆前端 / 后端 / 中间件模块；测试可拆接口 / 性能 / 自动化）。
7. 有线上访问地址/开源仓库的，在项目中标注。
8. 结构示例：项目名（时间｜角色，S/T）；背景与技术栈一句话（S）；主要动作：- …- …（A）；项目成果：…（R）。
9. 校园经历、无量化结果的经历：用「职责 + 具体动作 +（可确证的）规模/贡献」表述；若确无数字，不编造，用“参与 / 搭建 / 维护 N 个 / 覆盖 N 人”这类可确证的描述，并在“补充信息”环节引导用户补真实数字。

## G. 教育背景
1. 学校、专业、年份即可；不必写课程明细，不必单独占一整行。

## H. 内容难易与粒度（识别过简，并提升）
1. 判断整体水平：结合 JD 与候选情况判断这份简历是否“过简 / 缺乏含金量”——例如通篇都是低层琐碎操作（运维的单点排障 / 安装配置；开发的小工具 / 简单 CRUD；测试的重复用例），缺少有规模的成果、体系化 / 架构性内容，或缺少与目标岗位匹配的深度。
2. 过简即提示：诊断里给用户明确建议（如“整体内容偏简单，建议补充真实细节 / 更有含金量的项目 / 更具体的技术深度”，可归入「内容完整度 / 专业性」问题并附可补充建议），**严禁编造**。
3. 优化必须“提升”：把只写琐碎排障细节（端口冲突、调内存、换镜像源、安装配置、排查报错、单个简单运维操作）的内容合并、改写为**更高层次的结果 / 方案导向**表述（如“完成 XX 安全防护体系落地、实现 XX 自动化 / 规范化、建立 XX 链路”），不虚构事实与数字。
4. 不硬拔：若用户确实只有基础内容，则如实保留并突出其真实价值与岗位匹配点，不做无据拔高、不编造成果。
5. 避免“琐碎感”：删除 / 合并无信息量的过程性细节（如“安装依赖、升级版本、清缓存”），只保留能体现能力与结果的动作。

## I. 岗位与年限侧重
1. 按**用户选择/填写的目标岗位方向**（运维、云计算、SRE、DevOps、云原生、开发、测试、数据、产品等）决定优先级：把与该方向最相关的技能、项目放最前并写深入、写具体。
2. 从目标岗位的 JD 中提炼关键词（如运维岗的 K8s、监控、CI/CD、成本优化；开发岗的框架/中间件；测试岗的用例/自动化等），在技能与项目里自然体现；**无事实依据的关键词不得编造**。
3. 应届生：重基础（Linux / 网络 / 脚本）、学习与动手能力、实习 / 项目 / 竞赛细节；少用“负责”类笼统句，多写“具体做了什么、结果怎样”。
4. 1-3 年：重“能独立负责某块 + 带量产出”，突出工具熟练度与可量化的成果。
5. 资深：重架构设计、稳定性 / 高可用、故障治理、成本优化、容量与可观测性；用技术复杂度与规模说话，弱化罗列基础工具。

## J. 量化模板（只填真实数字）
1. 规模：覆盖 N 台服务器 / N 个集群 / N 个业务 / N 万用户。
2. 效能：发布 / 部署耗时从 X → Y（缩短 N%）；人天减少 N；告警 / 请求处理时间降到 N 分钟。
3. 成本：月 / 年成本降低 N 元或 N%（如每天 200-300 元 → 10-15 元）。
4. 稳定性：可用性 99.x%；故障发现 / 恢复时间 N 分钟；故障率 / 事故数从 N → M。
5. 产出：N 个变更 / 脚本 / 文档沉淀；N 次技术分享；覆盖 N 个团队。
6. 校园 / 活动：服务器 / 设备数量（N 台）；培训 / 覆盖人数（N 人）；搭建或维护的项目数（N 个）；解决的问题数量（N 个）；竞赛 / 奖项（年份 + 名称 + 等级）。
7. 没有可靠数字时**不编造**，标为“尚未量化”并在补充信息环节引导用户补全。

## K. 篇幅约束
1. 整体尽量一页（内容确实多可两页或更多），**不刻意注水凑字数**。
2. 工作经历 / 项目经历各 ≤ 3 段；教育背景一行；个人优势 ≤ 4 条；每条尽量 ≤ 4 行。
3. 若某版块过短或与岗位关系弱，合并到相关版块（如把零散技能并入“专业技能”），避免单列占位。

## L. 评分锚点（五个维度通用分档，0-100）
1. 81-100：明确、有量化、与岗位强相关、结构清晰、无空话。
2. 61-80：基本清晰，有部分量化，匹配度中等，偶有空话或冗长。
3. 41-60：结构可辨但较乱，量化偏少，匹配一般，空话较多。
4. 21-40：版块混杂 / 信息缺失，几乎无量化，多条空话。
5. 0-20：信息严重不全或与目标岗位明显不符。
6. 打分时对照该档特征，避免凭整体印象给分；排版维度结合版块顺序、间距、层级、是否一页判断。
7. **克制**：分数要反映真实改动幅度——不要因“重排了版块 / 换了措辞”就把某维度抬到 ≥90；单维度 ≥95 需确属顶级并说明理由；优化前后差值应与实际变化一致，避免明显不符合改动的暴涨。
8. **评分与问题清单一致**：问题清单未提到的维度，原始分不应低于 80；某维度原始分 < 80，问题清单须至少有一条属于该维度的问题。避免“问题清单没提排版，排版却涨了十几分”的相互矛盾。

## H. 输出原则
1. 每个板块按“用户原文”逐项呈现“原始 → 优化后”，优化后说明改了什么。
2. 只做表达与结构优化，不改变事实。
3. 用户输出不得提及本规则、案例来源或内部资料。
4. 输出前自检（缺一不可）：① 技能已去重并分类；② 无空话（主观形容词都有事实支撑）；③ 每条工作/项目有结果或量化；④ 版块按标准顺序、间隔清晰；⑤ 与目标岗位的关键词有自然命中；⑥ 整体基本一页、无过度注水。
5. 诊断/问题里的每条“建议”都要给出**一个可照抄的改写示例**（原文 → 改写），不要只写抽象动作。
6. 诊断结论先给**整份简历总体评价**，要**有含金量**：点出具体亮点、具体短板、整体水平判断、明确下一步方向，避免空话套话；再**分区域说明优点与不足**（基本信息/教育、专业技能、工作/项目、个人优势 各先写优点再写不足）。
